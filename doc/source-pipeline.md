# Исходники и серверные файлы

`src` содержит редактируемые файлы, `dist` — готовые файлы для сервера.

```text
yarn build : src → webpack → dist
yarn push  : yarn build → yarn _push → сервер
yarn pull  : сервер → dist → восстановление src
```

Сборкой управляет webpack. Дополнительного управляющего процесса и Gulp нет.

## Конфиги

В `src` поддерживаются JSON, JSON5 и YAML. В `dist` конфиги становятся обычным
JSON. Новые конфиги в `src` используют синтаксис JSON5 с расширением `.json`,
включая восстановление из серверного JSON и создание через dev API.

Явно выбранные `.json5` и YAML также поддерживаются и автоматически не
переименовываются. Семантически неизменившийся конфиг сохраняется побайтово,
поэтому `pull` не переформатирует старый строгий JSON без изменения данных.

Это относится только к конфигам тем, дашбордов и дашлетов в `topic.<число>/`
(включая вложенные `dashboard.<число>/`) и кубов в `.cubes/`.
Обычные ресурсы за пределами этих каталогов, включая `.json`, `.json5`,
`.yaml` и `.yml`, сохраняют имена и точные байты. Они не разбираются как
конфиги и не проходят повторную сериализацию при сборке, pull или push.

Пример:

```text
src/ds_example/topic.1/dashboard.2/index.json  (JSON5)
                       ↓ build
dist/ds_example/topic.1/dashboard.2/index.json
```

Два исходника с одинаковым выходным именем, например `index.json5` и
`index.yaml`, считаются ошибкой. Значения должны быть представимы в JSON:
`NaN`, `Infinity` и нестандартные YAML-типы не поддерживаются.

Локальный сервер использует те же преобразования. API продолжает работать с
логическими именами `.json`, а изменения из интерфейса сохраняются в исходный
файл. Запись без изменения значений сохраняет исходный текст. При изменении
значений документ может быть пересериализован: комментарии и оформление при
этом не гарантируются.

## Восстановление кода из sourcemap

`yarn pull` скачивает JS и `.map` в `dist`, затем извлекает исходники проекта
из стандартных `sources`/`sourcesContent` карты. Ресурс `_sources.json` больше
не создаётся и не используется. Если он остался от старой сборки, восстановление
его игнорирует; обычный push с разрешённым удалением убирает его с сервера.

В новых сборках карта содержит исходный текст TS/TSX и связанных файлов.
Тексты загрузчиков, webpack runtime и `node_modules` не становятся исходниками
проекта. Исходники стилей могут находиться во вложенных картах css-loader.
Недостающие исходные файлы новая сборка добавляет в стандартные массивы карты
без изменения существующих mappings.

Восстановление проверяет пути, точки входа, зависимости и совпадение общего
исходника между бандлами. Неполную или неподдержанную карту нельзя считать
надёжным исходным проектом: такой ресурс остаётся готовым JS/map. Карта без
`sourcesContent` не позволяет восстановить исходные типы TypeScript.
JS и карту нужно публиковать вместе: стандартный sourcemap не содержит
контрольной суммы JS, поэтому проверить их побайтовое соответствие невозможно.

Файл `.bi-build.json` внутри восстановленной схемы содержит точки входа и
список принадлежащих бандлам исходников. Его следует хранить вместе с
исходниками в Git. Он не публикуется как обычный ресурс. Благодаря ему
вспомогательные TSX-компоненты не становятся отдельными бандлами.

Конфиги восстанавливаются из серверного JSON в JSON5 с расширением `.json`.
Исходные комментарии и YAML-оформление на сервере не хранятся; существующий
локальный текст сохраняется, если значения не изменились.

## Повторный pull и локальные изменения

Если значения конфига совпадают, локальный текст сохраняется. Состояние
предыдущего восстановления хранится в игнорируемой Git папке `.bi-sync`,
отдельно от `dist`, который очищается при сборке. Конфликтующие локальные
изменения не должны молча заменяться серверными: восстановление сообщает
конфликт до изменения `src`.

Флаги `resources`, `dashboards`, `cubes`, фильтры `include`/`exclude` и
`--no-remove` учитываются также при восстановлении. Если ресурсы отключены,
новый конфиг восстанавливается из JSON в JSON5; его прежние комментарии и
YAML-оформление недоступны.

Source maps и серверный JSON не позволяют вернуть комментарии или исходные
файлы, которых в них нет. Точное восстановление возможно при наличии
исходного текста в `sourcesContent`; автоматическое слияние произвольного
TSX/JSON5 не выполняется.

## Проверка

`yarn test:scripts` запускает тесты инфраструктуры через встроенный `node:test`. Тесты используют
временные каталоги и локальные данные; загрузка на рабочий сервер для
проверки не требуется.

Тесты проверяют сохранность обычных ресурсов, конфликты локальных изменений,
старые JSON-конфиги и цикл webpack → sourcemap → исходники → webpack.

## Локальное редактирование из браузера

Для разработки с локальным хостом:

```sh
# ~/pro/bi/web
yarn start --api=http://lomaster --port=3000
# ~/pro/bi/projects/clowns
yarn start --server=http://localhost:3000
```

Открывать http://localhost:3003. Включены resources, dashboards и cubes для
`^ds_clowns$`. Для включённых блоков записи конфигов и ресурсов обрабатываются локально;
необработанные записи этих сущностей и выделение next_id блокируются до
проксирования. Если `dashboards: false`, запросы dashboard_topics/dashboards/dashlets,
включая изменения и next_id, отправляются на сервер. При `cubes: false` так же
работают cubes/dimensions. При `resources: false` ресурсы обслуживает сервер.
После изменения config.json нужно перезапустить dev-сервер. Авторизация и чтение данных по-прежнему используют сервер.

Новые конфиги сохраняются как JSON5 в `.json`; существующие YAML и `.json5`
сохраняют свой формат. Обычные ресурсы
сохраняются байтами. Метаданные ресурсов, изменённые в браузере, сохраняются
локально в `.bi-sync/resource-metadata.json`; это служебное состояние не
попадает в публикуемые ресурсы. Скомпилированный из исходников JS нельзя
перезаписать, переименовать или удалить через браузер: API возвращает 409,
чтобы не потерять соответствие исходникам. Такой ресурс редактируется в src.
